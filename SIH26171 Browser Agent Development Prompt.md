# Project: SIH26171 — On-Device Visual Perception for Lightweight Browser Agents

## 1. Project Intention

I want to build a privacy-preserving, lightweight browser extension that acts as a perception and privacy layer for AI browser agents.

The main idea is:

- The browser extension should understand webpages locally.
- It should first use cheap and reliable methods such as DOM/accessibility information.
- It should use OCR or a lightweight vision model only when DOM information is insufficient.
- Sensitive information must be detected and protected locally before any information is communicated to an external/server-side AI agent.
- The server-side agent/LLM should mainly perform reasoning and planning.
- The browser extension should validate and execute the actions generated by the agent.
- The system should be capable of understanding online forms and filling them automatically while protecting sensitive user information.

The project should follow a **Local Perception + Local Privacy + Server Reasoning + Local Execution** architecture.

---

# 2. Main Requirements

The extension must support these core capabilities.

## Requirement 1 — Sensitive Data Protection

The extension must detect sensitive information locally before communicating webpage information to an AI agent.

It should identify sensitive information from:

### DOM-based information
Examples:

- password fields
- email fields
- phone number fields
- payment/card fields
- personal names
- addresses
- government-ID-like information
- other configurable PII

### Text-based information

Use pattern/regex-based detection where appropriate.

Examples:

- email addresses
- phone numbers
- card-number-like patterns
- other configurable sensitive patterns

### OCR-based information

If sensitive information exists inside an image, canvas, screenshot, or visually rendered content:

```text
Screenshot
    ↓
OCR
    ↓
Text
    ↓
PII detection
```

### Vision-based information

The system should eventually be capable of detecting visually sensitive objects such as:

- faces
- identity documents
- signatures
- other configurable sensitive regions

All sensitive information must be processed locally whenever possible.

# 3. Masking / Redaction

Before webpage information is sent to an external/server-side agent, sensitive information must be sanitized.

For text:

```text
Original:

Name: John Doe
Email: john@example.com
Phone: 9876543210

Sanitized:

Name: [PERSON]
Email: [EMAIL]
Phone: [PHONE]
```

For screenshots/images:

```text
Original screenshot
       ↓
PII detection
       ↓
Sensitive bounding boxes
       ↓
Mask / blur / replacement
       ↓
Sanitized screenshot
```

The original sensitive information must never be unnecessarily transmitted to the server.

The privacy engine should provide a clear boundary:

```text
RAW WEBPAGE DATA
       ↓
LOCAL PRIVACY ENGINE
       ↓
SANITIZED DATA
       ↓
SERVER / AI AGENT
```

---

# 4. Secret Tokenization for Form Filling

Simple masking is not sufficient when the AI agent needs to fill a form.

Therefore implement a local secret-token mechanism.

Example:

```text
Actual email:
john@example.com

Local representation:
SECRET_001
```

The server/LLM should only see:

```text
Email field → SECRET_001
```

If the agent generates:

```json
{
  "action": "fill",
  "element_id": "email_1",
  "value": "SECRET_001"
}
```

the extension should resolve the token locally:

```text
SECRET_001
     ↓
Local secret store
     ↓
john@example.com
```

and only then place the actual value into the webpage.

The server should never need access to the actual secret.

# 5. Requirement 2 — Webpage Perception

The extension must understand webpage information.

Use a two-stage perception architecture.

## Stage 1 — Lightweight perception

First use:

- DOM
- Accessibility tree where available
- HTML attributes
- element labels
- ARIA attributes
- element positions/bounding boxes
- OCR when appropriate
- lightweight computer-vision methods

The system should attempt to understand the page without running an expensive vision model.

Example:

```text
Webpage
   ↓
DOM Analyzer
   ↓
Buttons
Inputs
Links
Forms
Labels
Images
Text
   ↓
Structured Page Representation
```

---

# 6. Stage 2 — Vision Fallback

If Stage 1 cannot confidently understand the page, invoke a lightweight local vision model.

Example:

```text
DOM analysis
     ↓
Confidence sufficient?
     │
   ┌─┴─┐
  YES  NO
   │    │
   │    ▼
   │  OCR / Vision
   │    │
   └────┘
      ↓
Page Understanding
```

The vision model should NOT run unnecessarily.

The system should prioritize:

```text
DOM/A11y
    ↓
OCR/lightweight CV
    ↓
Vision model
```

This is important for:

- low latency
- low CPU/GPU usage
- low memory consumption
- lightweight browser execution

# 7. Requirement 3 — Online Form Perception

The extension must be capable of detecting and understanding online forms.

For every form field, identify semantic meaning.

For example:

```text
<input type="text" name="full_name">
```

should become:

```json
{
  "id": "field_01",
  "type": "input",
  "semantic": "NAME",
  "confidence": 0.98
}
```

Similarly:

```text
EMAIL
PHONE
PASSWORD
DATE
ADDRESS
CITY
STATE
COUNTRY
PINCODE
```

The semantic classifier should use multiple signals:

- input type
- name
- id
- placeholder
- label
- nearby text
- ARIA attributes
- autocomplete attributes
- DOM structure

Do not depend only on the HTML `type`.

# 8. Requirement 4 — Form Filling

The agent should be able to understand a user's task such as:

> "Fill this registration form."

The workflow should be:

```text
User request
      ↓
Browser extension
      ↓
Form perception
      ↓
Semantic field identification
      ↓
Privacy/token mapping
      ↓
Server-side reasoning if required
      ↓
Structured actions
      ↓
Local action validator
      ↓
Form filling
```

The server-side agent should return structured actions rather than arbitrary JavaScript.

Example:

```json
{
  "action": "fill",
  "element_id": "field_02",
  "value": "SECRET_001"
}
```

Other supported actions should eventually include:

```text
click
fill
select
scroll
navigate
wait
back
submit
```

---

# 9. Action Validation

Never directly execute arbitrary commands generated by the LLM.

Use:

```text
LLM
 ↓
Structured Action
 ↓
Local Action Validator
 ↓
Browser Executor
```

The validator must verify:

- element exists
- element is visible
- element is interactable
- action type is allowed
- element ID matches the current page
- secret token exists if required
- action follows the configured security policy

Only after validation should the browser action execute.

# 11. Unified Page Representation

Regardless of whether information comes from DOM, OCR, or vision, convert it into a common representation.

Example:

```json
{
  "page": {
    "title": "Registration Form"
  },

  "elements": [
    {
      "id": "e1",
      "type": "input",
      "semantic": "NAME",
      "label": "Full Name",
      "bbox": [100, 200, 300, 240],
      "source": "dom",
      "confidence": 0.98
    },
    {
      "id": "e2",
      "type": "input",
      "semantic": "EMAIL",
      "label": "Email",
      "bbox": [100, 260, 300, 300],
      "source": "dom",
      "confidence": 0.99
    }
  ]
}
```

The agent should reason over this unified representation instead of directly depending on raw webpage HTML.

# 13. Privacy Requirements

Privacy is a first-class requirement.

Implement these principles:

### Principle 1

Raw sensitive information stays on the device.

### Principle 2

Redaction happens before network transmission.

### Principle 3

Server receives only the minimum information required for reasoning.

### Principle 4

Secrets are represented using local tokens.

### Principle 5

The server must never be able to resolve the local secret tokens.

### Principle 6

Do not log sensitive values.

### Principle 7

Do not store passwords or sensitive information unnecessarily.

### Principle 8

The extension should clearly indicate when information is being sent to the server.

# 14. Performance Requirements

The solution should be lightweight.

Optimize:

- CPU usage
- GPU usage
- RAM
- inference latency
- screenshot size
- number of model invocations
- network payload size

Use the two-stage perception strategy to avoid unnecessary vision inference.

Implement caching where useful.

For example:

```text
Same page state
     ↓
Reuse previous perception
```

rather than repeatedly analyzing the entire page.

       ↓
